# 面试问答：STM32 + ESP8266 上华为云项目

> 每道题先讲"我当时怎么做的"，再讲"为什么这么做"。
> 这个项目的优势是**你有硬件照片和云平台日志**，讲的时候有实据，不是背出来的 Demo。

## Q1：整体链路是怎么走的？

小程序点下发 → 华为云 IoT 平台记录设备消息并推送给在线设备 → ESP8266 通过 MQTT 收到 →
UART 传给 STM32 → STM32 从接收缓冲区解析出内容 → OLED 显示。
上行反过来：STM32 采传感器 → 组包 → ESP8266 上报 → 云端可查。

加分点：强调这是**双向闭环**，不是单向上传的 Demo。

## Q2：为什么 ESP8266 不直接干完所有活，要挂一个 STM32？

职责分离：ESP8266 擅长联网，但 GPIO 资源、实时性、外设驱动能力弱；
STM32 负责传感器采集、显示驱动、业务逻辑。两个芯片各干擅长的事，
出问题时可以分开验证（ESP8266 单独 AT 测试联网，STM32 单独点屏）。
真实产品里这也是常见架构（通信模组 + MCU）。

## Q3：调试中最难的是什么？怎么定位的？

串口数据解析：ESP8266 送过来的是带 MQTT 前缀的完整报文字符串，不是裸数据。
要从中定位到有效字段、截取内容，还要处理缓冲区长度和边界。

定位方法：**先看云端日志**——如果云平台显示已下发且状态 200，说明云端到模组这一段是通的，
问题在设备端解析或送显；如果云端没记录，问题在小程序或网络侧。
用二分法把链路切成两段分别验证，比猜快得多。

## Q4：数据丢了怎么办 / 可靠性怎么保证？

诚实回答现状：课程实验层面用的是平台默认的 QoS 与重连机制，没有做应用层补传和离线缓存。
如果要产品化，会补三件事：
1. 应用层 ACK：设备收到并执行后回一条确认，云端未收到则重发
2. 关键指令幂等：同一条指令重复下发不会重复执行
3. 断网期间本地缓存，恢复后补传

## Q5：安全性呢？

实验用的是平台分配的鉴权方式，指令是明文内容。
生产环境要补：设备级证书/密钥、TLS 传输、主题级权限（设备只能订阅自己的主题）、
下发内容的长度与字符白名单校验（防止超长或异常字符把 OLED 显示搞崩）。

## Q6：这个项目和你其他项目有什么关系？

- 和 `esp32-qmi8658-attitude-monitor`：一样是嵌入式数据采集，但本地显示、没有联网
- 和 `esp32-attitude-iot-dashboard`：那个是 ESP32 直接 MQTT 上云（单芯片方案），
  这个是**STM32 + 通信模组**的双芯片方案

面试时能横向对比两个物联网方案的差异（单芯片 vs MCU+模组），说明你对架构选型有自己的判断，
而不是只会抄一个例程。

## Q7：如果重做，你会改进什么？

1. 把 ESP8266 的 AT 指令交互做成状态机 + 超时重试，现在的轮询式写法在弱网下容易卡死
2. 上行数据加上时间戳和序号，便于云端判断丢包与乱序
3. 传感器数据采集周期与上报周期解耦（本地高频采样、云端低频聚合，省流量）
